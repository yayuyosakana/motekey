# ADR-001: 画面文脈抽出にGemini Vision APIを採用

## ステータス

採用済み

## コンテキスト

F-001（画面コンテキスト取得機能）において、Broadcast Extensionがキャプチャした画面フレーム画像からLINEのチャット履歴をテキストとして抽出する必要がある。候補として以下の2つを検討した。

- **Apple Vision（VNRecognizeTextRequest）**: iOS標準のローカルOCRフレームワーク
- **Gemini Vision API**: Googleが提供するマルチモーダルLLM API

## 比較

| 観点                        | Apple Vision（ローカルOCR）                  | Gemini Vision API                            |
| --------------------------- | -------------------------------------------- | -------------------------------------------- |
| テキスト抽出                | 可能                                         | 可能                                         |
| 話者の区別（相手/自分）     | **不可**（生テキストのみ）                   | **可能**（LINEのUI構造を理解）               |
| 会話の流れの理解            | **不可**                                     | **可能**                                     |
| API呼び出し回数             | OCR後に別途Gemini呼び出しが必要（**計2回**） | **1回で完了**                                |
| メモリ使用量                | VNRecognizeTextRequest起動で**+15-20MB**     | **画像データ分のみ**（~0.15MB）              |
| ネットワーク                | 不要（オフライン可）                         | 必要                                         |
| コスト                      | 無料                                         | 従量課金（ハッカソン規模では無視できる）     |

## 決定

**Gemini Vision APIを採用する。**

## 理由

1. **話者区別が必須**: LINEの画面から「誰が何を言ったか」を正確に把握する必要がある。Apple VisionのOCRでは吹き出しの左右配置や色の違いを解釈できず、生テキストの羅列になってしまう。
2. **API呼び出し1回で完結**: Apple Visionを使う場合、OCR後にさらにGemini APIで文脈解析が必要になり、レイテンシとコードの複雑性が増す。
3. **メモリ制約との相性**: キーボードExtensionのメモリ上限（約50MB）の中で、Apple VisionのOCRエンジン（+15-20MB）を追加で起動するのはリスクが高い。Gemini Vision APIならサーバー側で処理されるため、デバイス上のメモリ消費はJPEGデータ分（~0.15MB）のみ。
4. **ネットワーク依存はトレードオフとして許容**: 後続のアスクユーザーQ1〜Q3一括生成・返信文生成でGemini APIを必ず呼び出すため、ネットワーク依存は既に前提。フォールバックとして手入力UIも用意する。

## 影響

- F-001の実装はGemini Vision APIのリクエスト/レスポンス設計に依存する
- ネットワーク未接続時はF-001が動作しないため、手入力フォールバックが必須
- Gemini APIのAPIキーが必要（MVPでは用途別4キー運用。未設定時のみ共通キーへフォールバック）
